# Information-systems-design
## 2. Аналитический обзор аналогов и готовых решений

Для автоматизации учёта публикационной активности кафедры рассмотрены существующие системы учёта научной деятельности и библиографические источники. При сравнении учитывались возможности ведения реестра публикаций, импорта данных из РИНЦ и Scopus, выявления дубликатов, формирования отчётности и интеграции с другими системами.

В качестве аналогов выбраны ИАС «ИСТИНА», система Activity, решения на платформе 1С и Elsevier Pure. Scopus и РИНЦ рассматриваются как источники публикационных данных.

### 2.1. Сравнение аналогов и готовых решений

| Решение | Возможности | Импорт из РИНЦ и Scopus | Ограничения |
|---|---|---|---|
| **ИАС «ИСТИНА»** | Учёт научной деятельности, публикаций и аналитических показателей | Необходимо проверить доступные интеграции | Возможны ограничения адаптации под требования кафедры |
| **Activity** | Учёт публикаций сотрудников университета и подготовка научной отчётности | Требует уточнения | Доступность внедрения в другой организации не подтверждена |
| **Решение на базе 1С** | Учёт публикаций, настройка справочников и отчётов | Зависит от конфигурации и доработок | Возможны дополнительные затраты на настройку |
| **Elsevier Pure** | Управление научной информацией, профилями исследователей и публикациями | Интеграция со Scopus предусмотрена; подключение к РИНЦ требует проверки | Коммерческое решение, стоимость определяется поставщиком |
| **Scopus и РИНЦ** | Библиографические сведения, данные об авторах и публикациях | Scopus предоставляет API; для РИНЦ возможны API и разрешённые выгрузки | Не заменяют единую внутреннюю систему учёта кафедры |

**Источники:**
- [ИАС «ИСТИНА»](https://istina.msu.ru/)
- [Elsevier Pure](https://www.elsevier.com/en-gb/products/pure)
- [Scopus API](https://dev.elsevier.com/sc_apis.html)
- [eLIBRARY.RU](https://elibrary.ru/)

Анализ показал, что существующие решения позволяют организовать учёт публикационной активности, однако конкретные возможности интеграции, стоимость и условия внедрения требуют дополнительной проверки. Scopus и РИНЦ целесообразно использовать как внешние источники данных.

Для проектируемой системы необходимо предусмотреть импорт библиографических сведений, сопоставление публикаций с сотрудниками по идентификаторам и другим признакам, выявление дубликатов и формирование сводных отчётов.

## 3. Альтернативные варианты концепции ИС

Рассмотрены три варианта автоматизации учёта публикационной активности кафедры.

### 3.1. Вариант A. Электронные таблицы и регламенты

Предполагается создание единого реестра публикаций в электронных таблицах и утверждение регламента сбора и проверки данных. Импорт из РИНЦ и Scopus выполняется посредством доступных файловых выгрузок. Дубликаты выявляются с помощью фильтров и формул, отчёты формируются на основе сводных таблиц.

- **Технологии:** Excel или аналогичные табличные редакторы.
- **Ориентировочные ресурсы:** команда из 2–3 человек.
- **Трудоёмкость:** 1–2 чел.-мес.
- **Стоимость создания:** 30–80 тыс. руб.
- **Эксплуатация:** 10–25 тыс. руб. в год.
- **Срок внедрения:** 2–4 недели.

**Достоинства:**
- низкая стоимость;
- быстрое внедрение;
- простота использования.

**Недостатки:**
- высокая доля ручного труда;
- риск ошибок и дубликатов;
- ограниченные возможности автоматизации и масштабирования.

### 3.2. Вариант B. Внедрение готовой системы

Предполагается использование специализированной системы учёта научной деятельности либо адаптация существующей корпоративной платформы. Рассматриваются ИАС «ИСТИНА», решения на базе 1С и другие подходящие продукты.

Система обеспечивает ведение реестра публикаций, учёт сотрудников, формирование отчётов и, при наличии соответствующих интеграций, импорт внешних данных. Возможности автоматического сопоставления авторов необходимо проверить для выбранного продукта.

- **Технологии:** готовая информационная система, настройка справочников, ролей и отчётности.
- **Ориентировочные ресурсы:** команда из 3–4 человек.
- **Трудоёмкость:** 3–6 чел.-мес.
- **Стоимость внедрения:** 150–400 тыс. руб.
- **Эксплуатация:** 60–150 тыс. руб. в год.
- **Срок внедрения:** 2–4 месяца.

**Достоинства:**
- наличие готовых функций;
- сокращение сроков разработки;
- возможность технической поддержки.

**Недостатки:**
- зависимость от поставщика;
- затраты на лицензии и интеграцию;
- ограничения адаптации под специфические требования кафедры.

### 3.3. Вариант C. Собственная разработка веб-приложения

Предполагается создание специализированного веб-приложения с единым реестром публикаций, модулем импорта из РИНЦ и Scopus, механизмами выявления дубликатов и сопоставления авторов, а также формирования отчётности.

- **Технологии:** Python (Django или FastAPI), PostgreSQL, веб-интерфейс.
- **Импорт данных:** через доступные API или разрешённые файловые выгрузки.
- **Ориентировочные ресурсы:** команда из 4–5 человек.
- **Трудоёмкость:** 6–10 чел.-мес.
- **Стоимость создания:** 400–800 тыс. руб.
- **Эксплуатация:** 50–120 тыс. руб. в год.
- **Срок внедрения:** 4–6 месяцев.

**Достоинства:**
- гибкая настройка под процессы кафедры;
- возможность реализации собственных алгоритмов сопоставления авторов;
- независимость от ограничений конкретного готового продукта.

**Недостатки:**
- высокая первоначальная стоимость;
- длительная разработка;
- необходимость самостоятельного сопровождения и тестирования.

### 3.4. Сравнение альтернативных вариантов

| Параметр | Вариант A | Вариант B | Вариант C |
|---|---|---|---|
| **Технологии** | Электронные таблицы | Готовая система | Веб-приложение |
| **Основной способ импорта** | Файловые выгрузки | Зависит от продукта | API или файлы |
| **Трудоёмкость, чел.-мес.** | 1–2 | 3–6 | 6–10 |
| **Создание/внедрение, тыс. руб.** | 30–80 | 150–400 | 400–800 |
| **Эксплуатация в год, тыс. руб.** | 10–25 | 60–150 | 50–120 |
| **Срок внедрения** | 2–4 недели | 2–4 месяца | 4–6 месяцев |
| **Основное преимущество** | Экономичность | Быстрый запуск готовых функций | Гибкость |
| **Основной недостаток** | Ручная обработка | Зависимость от поставщика | Высокие затраты на разработку |

### 3.5. Выводы по альтернативным вариантам

Таким образом, вариант A подходит для небольшого объёма публикаций и ограниченного бюджета, вариант B — для быстрого внедрения при наличии подходящего готового решения, вариант C — для реализации специфических требований кафедры.

Окончательный выбор выполняется на основании многокритериальной оценки с учётом стоимости владения, полноты функций, интеграции, безопасности и масштабируемости.

## 5. Описание выбранной концепции и модель процессов TO-BE

### 5.1. Краткое описание выбранного варианта

**Вариант C — специализированное веб-приложение для учёта публикационной активности кафедры.**

**Идея решения:** единая веб-платформа с автоматическим импортом метаданных публикаций по DOI из внешних источников (РИНЦ, Scopus), встроенными механизмами выявления дубликатов и сопоставления авторов, а также модулем формирования отчётов для НИЧ.

**Автоматизируемые функции:**
- регистрация и ведение реестра публикаций сотрудников кафедры;
- автоматический импорт библиографических данных по DOI через API РИНЦ и Scopus;
- выявление дубликатов и сопоставление публикаций с сотрудниками по идентификаторам (Author ID, ORCID) и эвристическим правилам;
- формирование сводных отчётов по показателям эффективности (число публикаций, квартили, индекс Хирша);
- разграничение ролей: научный сотрудник, заведующий кафедрой, сотрудник НИЧ.

**Архитектура и технологии:**
- Backend: Python (FastAPI), REST API;
- Frontend: веб-интерфейс на React/Vue.js;
- База данных: PostgreSQL;
- Интеграции: API РИНЦ (eLIBRARY), Scopus API, система единой учётной записи вуза (SSO);
- Размещение: серверы вуза (требование по 152-ФЗ).

**Ресурсы (из Раздела 3):** команда 4–5 человек, трудоёмкость 6–10 чел.-мес., стоимость создания 400–800 тыс. руб., эксплуатация 50–120 тыс. руб./год, срок внедрения 4–6 месяцев.

### 5.2. Модель процесса TO-BE (BPMN)

Целевой процесс «Учёт публикации сотрудника кафедры» после внедрения ИС.

![Модель процесса TO-BE](bpmn_to_be.png) 

Процесс включает четыре участника (дорожки): научный сотрудник инициирует добавление публикации, информационная система автоматически загружает метаданные из РИНЦ/Scopus и выявляет дубликаты, заведующий кафедрой проверяет спорные случаи, НИЧ формирует отчёты по запросу. Границы системы показаны на диаграмме: автоматизированы импорт данных, поиск дубликатов и формирование отчётов; вручную остаются инициация процесса и экспертная проверка спорных дублей.

### 5.3. Связь с проблемами AS-IS

Внедрение выбранного варианта устраняет следующие проблемы текущего процесса (AS-IS):

| Проблема AS-IS | Как устраняется в TO-BE |
|---|---|
| Ручной ввод метаданных публикаций (название, авторы, журнал) | Автоматическое заполнение по DOI через API РИНЦ/Scopus |
| Дубликаты из-за разночтений в написании ФИО авторов | Алгоритм сопоставления по Author ID, ORCID и эвристикам |
| Долгое формирование отчётов для НИЧ (вручную, в конце года) | Автоматическое формирование отчётов по запросу в реальном времени |
| Потеря публикаций при смене сотрудников | Централизованный реестр, привязанный к учётной записи вуза |

### 5.4. Границы системы

**Автоматизируется ИС:**
- импорт метаданных из внешних источников;
- поиск и пометка дубликатов;
- формирование отчётов;
- разграничение доступа по ролям.

**Остаётся ручным:**
- первичная инициация процесса (сотрудник вводит DOI или загружает файл);
- ручная проверка спорных дубликатов и неопознанных авторов заведующим кафедрой (экспертное решение).
